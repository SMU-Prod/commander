# Auditoria CMO — Commander (2026-08-12)

Escopo: produção real (https://commander-tau.vercel.app) + código-fonte em `C:\Users\erick\GEST-NAV\web`. Auditoria de mercado, só leitura — nenhuma alteração feita além deste arquivo.

Formato: **P0** perde cliente hoje · **P1** resolver antes de divulgar em escala · **P2** backlog de crescimento.

---

## 1. A landing real

Página lida direto da URL (`app/page.tsx`, hero + 3 blocos de valor + como funciona + seção fundador + footer).

**P0 — Contador de vagas mostra "Restam 100 de 100"**
Evidência: `get_page_text` na produção retorna literalmente `Restam 100 de 100 vagas`. Um contador de escassez em 100% de capacidade comunica o oposto do que promete: zero tração, não urgência. Para quem chega frio (dono de Azimut 50 nunca ouviu falar do produto) isso lê como "ninguém comprou ainda".
Proposta: não mostrar o contador até haver pelo menos ~5-10 fundadores reais, ou trocar a moldura por algo que não dependa de tração ("lançamento — seja o fundador #1") enquanto o número é zero.

**P0 — Zero prova social**
Evidência: página inteira (`app/page.tsx`) não tem nenhum depoimento, nome de marina, nome de barco real além do mock ("Blue Horizon", que é claramente um exemplo de produto, não um cliente). Não há logos de parceiros, não há "X embarcações já cadastradas". Navionics/planilha do marinheiro não perdem nada aqui — a página não dá nenhum motivo de confiança externo, só a promessa do próprio produto.
Proposta: assim que houver 3-5 fundadores reais, trocar o mock por depoimento curto com nome+barco+marina (com autorização).

**P1 — Mobile: hero é só texto, sem prova visual acima da dobra**
Evidência: `MockTelas` (mock do app) vem depois do H1/CTA no grid `lg:grid-cols-[1.1fr_1fr]` — em mobile o layout empilha, então o mock cai abaixo do fold em telas menores antes do primeiro scroll. Quem decide em 5s pode não ver o produto de verdade antes de rolar.
Proposta: confirmar no dispositivo real que o card "TUDO EM DIA / BLUE HORIZON" aparece nos primeiros ~600px de mobile; se não aparece, subir a prioridade dele no DOM mobile.

**P1 — Preço ancorado é convincente, mas some no CTA do topo**
Evidência: o CTA do hero (`Quero ser fundador`) só ancora via scroll até `#fundador` — quem não rola não vê `R$ 119,90 → R$ 69,99`. A âncora de preço é o argumento mais forte da página e está a 2 telas de distância do primeiro CTA.
Proposta: considerar um selo pequeno perto do CTA do hero ("a partir de R$ 69,99/mês") sem duplicar a seção inteira.

## 2. Funil completo no código

Rastreado: `app/page.tsx` → `app/(auth)/login/page.tsx` + `lib/acoes/auth.ts` → `app/onboarding/page.tsx` → `app/(app)/hoje/page.tsx` → `app/(assinatura)/assinar/page.tsx`.

**P0 — "Confirm email" ligado quebra o funil de cadastro**
Evidência, `lib/acoes/auth.ts`:
```
// Confirm email ligado: signUp cria o usuario mas NAO abre sessao — sem este
// aviso a pessoa seria devolvida ao login sem explicacao nenhuma.
if (!data.session) {
  redirect(`/login?aviso=...Enviamos um link de confirmação para o seu e-mail...`)
}
```
Isso confirma o que a memória do projeto já sinalizava como pendente ("Confirm email OFF"): hoje, todo cadastro novo é interrompido — sai do fluxo, precisa abrir o e-mail, achar o link, voltar. Para tráfego pago/frio isso é o maior ralo do funil: cada clique extra fora do app derruba conversão de forma desproporcional. Não consegui confirmar via este ambiente se o toggle já foi desligado no Supabase de produção (fora do escopo de leitura de código) — mas o comentário no código descreve o comportamento como ativo hoje.
Proposta: desligar "Confirm email" no Supabase Auth de produção (ou trocar por magic link) antes de qualquer push de mídia paga.

**P1 — Onboarding pede motor/horas/vencimentos antes do primeiro valor**
Evidência: `app/onboarding/page.tsx`, 3 seções obrigatórias-mas-não (`nome` do barco é o único `required`) — estaleiro, modelo, ano, marina, motores, horas BB/BE, seguro, TIE. Mesmo com "o resto você completa depois" no subtítulo, é uma tela longa (94 linhas de form) antes de qualquer recompensa.
O "aha" real é rápido depois disso: `/hoje` (511 linhas) já entrega anel de status, alertas, boletim do mar, atalhos — muito rico. O gargalo não é o pós-onboarding, é a barreira de entrada do formulário em si.
Proposta: testar reduzir a etapa 1 do onboarding a nome + 1 vencimento crítico, empurrando motor/horas para o primeiro "Registrar" dentro do app (a tela `/hoje` já lida bem com dados parciais — ver bloco "Falta informação").

**P1 — Sem trial/paywall visível no código hoje, mas a chave já existe**
Evidência: `app/(app)/layout.tsx` só aplica o gate de cobrança se `NEXT_PUBLIC_COBRANCA_ATIVA === "1"`. Não deu para confirmar o valor real em produção (Vercel env não acessível nesta sessão — ver nota de conta). Se a flag estiver desligada, hoje qualquer usuário logado usa o produto de graça indefinidamente sem nunca precisar passar por `/assinar` — isso é bom para adoção mas péssimo se ninguém está de olho na conversão de fundador (a régua "100 vagas" só avança quando alguém realmente assina).
Proposta: confirmar o valor de `NEXT_PUBLIC_COBRANCA_ATIVA` em produção; se estiver "0", decidir deliberadamente até quando (não por esquecimento).

**P2 — `/assinar` pede CPF sem explicar por quê antes do formulário**
Evidência: `app/(assinatura)/assinar/page.tsx` já tem a frase certa ("Exigido pelo sistema de pagamento para emitir a cobrança") — isso é bom, mas está como legenda pequena depois do campo, não antes. Ajuste menor.

## 3. Motores de crescimento que já existem no produto

**Compartilhar saída (Strava social) — existe e funciona, mas está enterrado**
Evidência: `app/(app)/diario/[id]/compartilhar-botao.tsx` usa Web Share API com fallback de clipboard, texto gerado por `lib/domain/compartilhar.ts` ("Saída de X MN em Yh — Origem → Destino, pelo Commander"). É uma implementação madura (trata cancelamento, trata dado parcial). Mas: só aparece na página de detalhe de uma saída já registrada (`/diario/[id]`) — não há nenhum convite pra usar isso na hora que a saída termina, nem no card "Seu ano no mar" do `/hoje` (que mostra totais anuais mas não tem botão de compartilhar ali).
Proposta: adicionar CTA "Compartilhar" direto no card "Seu ano no mar" de `/hoje`, e considerar um toast pós-salvamento de saída ("Saída registrada — compartilhar?").

**Convite de tripulação — o loop viral mais forte do produto, e já tem WhatsApp embutido**
Evidência: `app/(app)/menu/tripulacao/page.tsx` gera link (`/convite/[codigo]`) e já monta a mensagem de WhatsApp pronta (`Entre na tripulação da {embarcacao} no Commander: {link}`). O fluxo de aceite (`app/(app)/convite/[codigo]/page.tsx`) é limpo. Isso é o gancho comandante-convida-dono (ou dono-convida-comandante) que mais se parece com um loop viral de verdade no produto — mas hoje só é descoberto por quem já entrou em `/menu/tripulacao`, uma tela de configuração, não um momento de produto.
Proposta: no `/hoje`, o card "Só você tem acesso a este barco" já linka pra lá — bom. Faltou reforçar esse convite no onboarding (passo 4 opcional: "convide seu comandante agora") e no e-mail/mensagem pós-cadastro, onde a intenção está mais quente.

**Selo Ouro — status social pronto, mas invisível fora de `/barco/selo`**
Evidência: `app/(app)/barco/selo/page.tsx` tem checklist de completude + pedido de avaliação presencial — bem construído. Porém: não aparece no `/hoje` (a tela mais visitada), não aparece na landing como aspiração ("ganhe o Selo Ouro"), e não há nenhuma vitrine pública de quem já tem o selo (o marketplace de comandantes mostra "Verificado" pendente, mas não há equivalente pro Selo Ouro do barco).
Proposta: um badge pequeno no `CardEmbarcacao` de `/hoje` quando o selo é concedido (o status social só funciona se for visto), e citar "Selo Ouro" como aspiração na seção de valor da landing.

**Corredores/sondagem — a narrativa "cada barco melhora o mapa" existe tecnicamente, mas não é vendida como comunidade**
Evidência: `components/mapa/navegar-mapa.tsx:1278` tem a copy "Contribuir com o mapa de corredores... Ajuda outros barcos a encontrar caminho" — é opt-in, correto sobre privacidade (agregado, anônimo), mas é uma linha de checkbox dentro do fluxo técnico de gravar trilha. Não há contador de contribuição ("você já ajudou a mapear X células"), não há menção nenhuma disso na landing nem no `/hoje`, e o SonarChart-like (`SondagemPainel`) só aparece pra quem já está navegando ativamente.
Proposta: expor um número simples em algum canto do app pós-saída ("Sua trilha ajudou a mapear 4 novas áreas") — é a peça que falta pra virar orgulho de comunidade em vez de feature técnica escondida.

## 4. Canal do sócio (parceiros comerciais)

**P0 — Não existe página de vendas para o parceiro, só um formulário logado**
Evidência: o link do footer da landing (`Para marinas, pousadas e restaurantes`) vai direto para `/parceiro`, que por sua vez é **gate de login** (`app/(parceiro)/parceiro/page.tsx`: `if (!user) redirect("/login?volta=/parceiro")`) e, uma vez logado, cai direto no formulário de edição de perfil (categoria, preço, fotos) — não numa página que explica o que o parceiro ganha, quanto custa, como funciona. Não há nenhuma versão pública/institucional de `/parceiro`.
Isso significa que o Pedro **não tem nada para mostrar no celular numa reunião de 10 minutos numa marina**: ele teria que criar uma conta, logar, e mostrar o formulário de cadastro como se fosse o "pitch" — o que não vende nada, só configura.
Proposta: criar uma página pública `/parceiro` (ou `/para-marinas`) com a proposta de valor (aparecer no mapa de quem já é dono de barco 40-60 pés, visualizações reais, sem mensalidade de agência) e mover o formulário logado para `/parceiro/painel`.

**P1 — O contador de visualizações é a melhor prova que existe, e está trancada atrás do login**
Evidência: `app/(parceiro)/parceiro/page.tsx` linha ~55-62 mostra `{p.visualizacoes} proprietário(s) viu(ram) seu perfil` — esse número é exatamente o gancho de venda ("X donos de barco já olharam seu perfil este mês"), mas só o próprio parceiro cadastrado o vê, depois de já ter entrado. Não serve para fechar o primeiro parceiro.
Proposta: usar esse tipo de métrica (agregada, ex. "N proprietários usam o Commander na Baía de Guanabara") na futura página pública de vendas do item acima.

**P2 — Categorias do parceiro (marina/posto/pousada/restaurante) não têm nenhuma antecipada em "poitas" como atrativo de marketing**
Evidência: o formulário já modela poita, calado máximo, traslado, vaga cortesia — dado rico — mas nada disso aparece narrado como vantagem em lugar nenhum público. É só schema de formulário.

## 5. Fundação de aquisição

**SEO técnico** — checado ao vivo em produção:
- `title`: "Commander — o dossiê do seu barco" — bom, claro, mas não usa palavra-chave "barco"/"lancha"/"embarcação Rio de Janeiro" nenhuma vez além do óbvio. Sem termo geográfico.
- `description`: "Manutenção em dia, documentos alertados e um histórico que vale dinheiro na hora de vender." — boa, dentro do limite.
- `og:title`/`og:description`: iguais ao `title`/`description` (`app/layout.tsx`), `locale: pt_BR`, `type: website` — corretos.
- **P1 — Sem `og:image` nenhuma.** Nem estática (`public/`) nem dinâmica (`opengraph-image.tsx`/`.png`) em nenhum lugar de `app/`. Confirmado por busca no projeto inteiro — zero arquivos de OG image.
- `robots.ts`: bloqueia corretamente todas as rotas autenticadas (`/hoje`, `/barco`, `/diario` etc.) e libera só `/`. Correto e defensivo.
- `sitemap.xml`: em produção, só uma URL (`https://commander-tau.vercel.app`, `priority: 1`). Coerente com o app ser majoritariamente autenticado, mas se `/parceiro` virar página pública (item 4), ela deveria entrar aqui.

**P0 — Sem imagem de compartilhamento no WhatsApp**
Evidência direta da ausência de `og:image`: quando o Pedro manda o link do Commander num grupo de WhatsApp do iate clube, o preview vem só com título+descrição em texto, sem nenhum card visual — no canal onde essa audiência mais confia (indicação de amigo), a primeira impressão é a mais fraca possível tecnicamente.
Proposta: gerar uma `opengraph-image.tsx` (Next.js `ImageResponse`) reaproveitando a mesma composição do mock do hero ("TUDO EM DIA / BLUE HORIZON") — 1 arquivo, resolve landing + todo link futuro.

**P2 — PWA instalável, mas sem convite nenhum pra instalar**
Evidência: `app/manifest.ts` está completo (ícones 192/512/maskable, `display: standalone`), mas busca por `beforeinstallprompt`/"adicionar à tela" no projeto inteiro só retorna o próprio manifest — nenhum componente de UI convida o usuário a instalar. `start_url: "/hoje"` é uma boa escolha (não a landing) para quem já é usuário.
Proposta: banner leve de instalação depois do 2º ou 3º acesso logado (não no primeiro — deixar a pessoa confirmar valor antes de pedir espaço na tela inicial).

**Régua do que não prometer** — cobrança (`assinar`) e o gate de billing (`NEXT_PUBLIC_COBRANCA_ATIVA`) ainda são condicionais/não confirmados em produção nesta auditoria; a landing já é honesta nisso (não promete nada além do que o produto mostra: alertas, diário, marketplace de comandantes). O único risco de promessa adiantada é o próprio contador de vagas em 100/100 (item 1) — ele promete escassez que ainda não existe.

## Os 5 que eu faria primeiro

1. Desligar "Confirm email" no Supabase Auth de produção (ou trocar por magic link) — é o ralo mais caro do funil, mata cadastro antes mesmo do onboarding.
2. Gerar uma `og:image` (Next `ImageResponse`, reaproveitando o mock do hero) — resolve o compartilhamento no WhatsApp, o canal de aquisição mais barato que este público tem.

4. Criar uma página pública de vendas para `/parceiro` (separada do formulário logado) — hoje o Pedro não tem nada pra mostrar numa marina.
5. Cortar a etapa 1 do onboarding para nome + 1 vencimento crítico, empurrando motor/horas pro primeiro uso real dentro do `/hoje`.
