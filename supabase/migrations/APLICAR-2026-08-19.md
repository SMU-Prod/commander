```sql
  (select count(*) from public.bases_operacionais)                         as bases,             -- 0
  (select count(*) from pg_policies where schemaname = 'public')           as policies;          -- 218
```

2. **Uma migration por vez.** Cada uma é um `begin; … commit;` — rode, confira, só então
   passe para a próxima. Não emende as sete.
3. Todas são idempotentes (`create or replace`, `drop policy if exists`). Reaplicar não quebra.
4. Depois de aplicar, rode o app e faça um login real. RLS não tem teste automatizado aqui:
   a conferência de que nada trancou é abrir uma embarcação e ver o diário, as fotos e o financeiro.

**Confere que ninguém foi trancado (tem de voltar 0):**
```sql

```

**Confere que as três continuam DEFINER com search_path fixo (tem de voltar 3):**
```sql
select count(*) from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public'
   and p.proname in ('permissao','pode_ver_embarcacao','eh_prop')
   and p.prosecdef
   and array_to_string(p.proconfig, ',') like '%search_path%';
```

**Teste de fumaça, com um login real:** abra uma embarcação e confirme que o diário,
as fotos, os documentos e o financeiro carregam normalmente. Se qualquer tela vier
vazia, reverta — é sinal de que algum vínculo tem `suspenso_em` inesperado.

**Reverter** (volta exatamente à definição que estava viva em 19/08/2026):
```sql
begin;

create or replace function public.permissao(emb uuid, aba text, modo text)
returns boolean language sql stable security definer set search_path to 'public'
as $function$
  select exists (
    select 1 from public.vinculos v
    where v.embarcacao_id = emb
      and v.usuario_id = auth.uid()
      and (
        v.papel = 'PROP'
        or coalesce((v.permissoes -> aba ->> modo)::boolean, false)
      )
  );
$function$;

create or replace function public.pode_ver_embarcacao(emb uuid)
returns boolean language sql stable security definer set search_path to 'public'
as $function$
  select exists (
    select 1 from public.vinculos v
    where v.embarcacao_id = emb and v.usuario_id = auth.uid()
  );
$function$;

create or replace function public.eh_prop(emb uuid)
returns boolean language sql stable security definer set search_path to 'public'
as $function$
  select exists (
    select 1 from public.vinculos v
    where v.embarcacao_id = emb and v.usuario_id = auth.uid() and v.papel = 'PROP'
  );
$function$;

drop policy if exists "auditoria: registra em nome proprio, na embarcacao que acessa" on public.auditoria;
create policy "auditoria: registra em nome proprio, na embarcacao que acessa"
  on public.auditoria for insert to authenticated
  with check (
    autor_id = auth.uid()
    and exists (select 1 from public.vinculos v
                where v.embarcacao_id = auditoria.embarcacao_id
                  and v.usuario_id = auth.uid())
  );

commit;
```

## 2 · `068_viagens_e_sondagens_pela_matriz.sql`

`viagens` sai de uma policy `FOR ALL` que só pedia vínculo e passa a quatro policies

exclusão passam a ser de quem levantou.

**Confere (tem de voltar 8 linhas — 4 de cada, todas `{authenticated}`):**
```sql

  from pg_policies
 where schemaname = 'public' and tablename in ('viagens','sondagens')
 order by tablename, cmd;
```

**Confere que a viagem existente continua visível para o dono (tem de voltar 1):**
```sql

 where exists (select 1 from public.vinculos x
               where x.embarcacao_id = v.embarcacao_id and x.papel = 'PROP');
```

**Teste de fumaça:** abrir o diário de bordo e ver a viagem listada; abrir a carta e
ver as sondagens.

**Reverter:**
```sql
begin;
drop policy if exists "viagens: ver pela matriz" on public.viagens;
drop policy if exists "viagens: criar pela matriz" on public.viagens;
drop policy if exists "viagens: atualizar pela matriz" on public.viagens;
drop policy if exists "viagens: excluir pela matriz" on public.viagens;
create policy "viagens: tudo com vinculo" on public.viagens
  for all using (pode_ver_embarcacao(embarcacao_id))
  with check (pode_ver_embarcacao(embarcacao_id));

drop policy if exists "sondagens: ve as do barco" on public.sondagens;
drop policy if exists "sondagens: grava a propria" on public.sondagens;
drop policy if exists "sondagens: corrige a propria" on public.sondagens;
drop policy if exists "sondagens: apaga a propria" on public.sondagens;
create policy "sondagens: dono grava e le as suas" on public.sondagens
  for all using (pode_ver_embarcacao(embarcacao_id))
  with check (pode_ver_embarcacao(embarcacao_id) and usuario_id = (select auth.uid()));
commit;
```

## O que este lote NÃO cobre

Registrado para não se perder — está detalhado na auditoria:

- **P1-6 · o link de cotista não tem como ser resgatado.** Não existe
  `aceitar_convite_cotista()`, e `aceitar_convite()` cria vínculo com `papel = 'CMDT'`
  fixo. Ninguém consegue entrar como COTISTA. Fechar isso exige decidir o desenho
  (vaga de cota, prazo do código) **e** mexer na rota `/convite/[codigo]` — não é só
  migration, e por isso ficou fora.
- **P1-5(a) · estoque, tanques e bases pertencem a uma pessoa, não à empresa.**
  Redesenho de produto.
- **P2-4 · os 15 índices de chave estrangeira** do BLOCO 7 da auditoria.
  `create index concurrently` não roda dentro de transação — se forem aplicados, tem de
  ser soltos, fora de migration transacional.
- **Fora do SQL:** ligar o *Leaked password protection*, confirmar que *Confirm email*
  está ligado (`gold_reivindicar_consultor()` confia no e-mail do JWT), e decidir sobre
  a idempotência dos contadores de publicidade.

## Nota sobre a numeração das migrations

O diretório tem 67 arquivos (`001` a `066`, com `033` duplicado em
`033_connect_interesses` e `033_gold`). O remoto tem **117 migrations aplicadas**. Os
números não batem porque **o mesmo arquivo foi aplicado fatiado em várias migrations
remotas** — `048_planos_assinatura` virou 8 partes, `049_admin_papeis` virou 7,
`050_avaliacoes_gold_porte` 5, `044_agenda` e `046_marketplace_demandas` 4 cada, e
`041_campos_finais_prd.sql` foi dissolvido em ~10 migrations nomeadas por assunto
(`contatos_empresa_email_observacoes`, `eventos_local_saida_passageiros`, …). Há também
nomes que divergem entre arquivo e remoto (`023_avisos_gerais.sql` →
`avisos_gerais_alertas_enviados`; `039_transferencia_embarcacao.sql` →
`038_transferencia_embarcacao`).

**Consequência prática:** `supabase db push` não é confiável aqui, e o histórico remoto
não reconstrói o diretório. Estas migrations seguem a numeração **do diretório**
(último real = `066_cotista_envios_e_afazeres.sql`, daí `067`), e devem ser aplicadas
**por SQL direto**, como as rodadas anteriores.

```sql
create or replace function public.publicidade_registrar_impressao(p_campanha_id uuid)

  values (p_campanha_id, public.hoje_sp(), 0, 1)
```

> **NÃO cole este arquivo inteiro no editor e mande executar.** `create index
> concurrently` é proibido dentro de bloco de transação — o Postgres levanta
> `25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. É
> exatamente por isso que ele não entrou em nenhuma das migrations numeradas: as quatro
> acima são `begin; … commit;`.
>
> **Cole UM comando, execute, confira "Success", cole o próximo.** São 8.

`concurrently` não bloqueia escrita — é seguro com gente usando o app. Em troca, um
comando interrompido no meio deixa um índice **inválido** para trás.

**Critério:** medidas **86 FK sem índice** em 189 chaves estrangeiras. Foram criados
**8**; os outros **78 foram descartados** por não ter nenhuma consulta atrás — cada um

## O que este lote resolve SEM SQL

Três achados eram de código e de documentação, e não têm migration:

- **A-11 · `NEXT_PUBLIC_COBRANCA_ATIVA` era código morto documentado como passo
  obrigatório.** O gate global saiu na onda 47 e a variável não era lida em lugar nenhum
  — mas `docs/OPERACAO.md` mandava ligá-la, e quem seguisse a doc acharia que tinha
  ligado a cobrança. Retirada de `web/.env.example` e dos passos 2 e 7 do roteiro de
  deploy; o comentário morto em `web/app/(app)/layout.tsx` foi encurtado para dizer o que
  importa (o paywall é por recurso, não por aplicativo) sem citar a variável.
- **A-12 · duas definições da máquina de estados do Gold.** O webhook saltava
  `aguardando_pagamento → aguardando_agendamento`, transição que `gold_transicao_valida`
  (banco) e `TRANSICOES` (`lib/domain/gold.ts`, com teste) consideram inválida.
  **Decisão: o webhook cedeu**, e passou a dar os dois passos
  (`aguardando_pagamento → pago → aguardando_agendamento`). Declarar o salto na RPC
  consertaria uma definição e quebraria a outra, apagaria um estado que a tela do cliente
  mostra, e concederia o atalho também ao Suporte pela tela. Nenhuma migration: o banco
  já estava certo.

  tabela não liberava nada; `plano_do_usuario()` (a função que a RLS usa para limite de

  um Gold **já concede Commander** pela validade do selo. Corrigido na doc, com a
  consequência operacional escrita por extenso.
